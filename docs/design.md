## 1. 背景

開発者は日々、プロジェクトごとに決まった CLI コマンドを繰り返し実行します
（`prisma migrate dev --name ...`、`docker compose up -d`、`terraform apply` など）。
これらは「長い」「引数を覚えていない」「プロジェクトによって微妙に違う」ため、
シェル履歴の検索や手元のメモ、`Makefile`、エイリアスなどに散らばりがちです。

既存手段にはそれぞれ不足があります。

- **シェル履歴 / エイリアス**: マシンローカルで、プロジェクトに紐づかない。チームで共有できない。
- **Makefile / package.json scripts**: 言語・エコシステムに縛られる。パラメータ入力や破壊的操作の確認といった実行時の体験は作り込みが要る。
- **スニペットマネージャ**: 検索はできても、安全な実行（引数配列・中断・終了コード伝播）まで面倒を見てくれない。

**shiori**（栞 / bookmark）は、よく使うコマンドをプロジェクトのルートに置く設定ファイルに登録し、
検索・実行・管理する小さな OSS ツールです。名前のとおり「コマンドに栞を挟む」ことを狙います。
最終的に CLI / TUI（Bubble Tea）/ GUI（Wails）の 3 つの入り口を持ちますが、
ドメインロジックは単一のコアパッケージに閉じ込め、どの UI にも依存させません。

## 2. 目標（Goals）

- G1. プロジェクトルートの設定ファイルにコマンドを登録し、`shiori list` で一覧できる。
- G2. `shiori run <name>` で、**シェルを経由せず**引数配列としてコマンドを実行できる。
- G3. 子プロセスの終了コードをそのまま shiori の終了コードとして返す。
- G4. `Ctrl+C`（SIGINT）による中断を子プロセスまで正しく伝える。
- G5. パラメータ付きコマンドをテンプレートとして登録でき、**インジェクションが構造的に起きない**。
- G6. パイプ・リダイレクトが必要なコマンドのみ、設定で `shell: true` を明示したときだけシェル経由で実行できる。
- G7. 破壊的コマンドに実行前確認を挟める。
- G8. パラメータ値や環境変数を、ログ・エラーメッセージに不用意に出さない。
- G9. コアロジックは UI 非依存で、CLI / TUI / GUI から同一 API で呼べる。

## 3. 非目標（Non-goals）

これらは「今はやらない」ことを明示するものです（将来の検討は妨げません）。

- N1. コマンドの**リモート同期・共有サーバ**。設定ファイルは Git などでユーザーが共有する前提。
- N2. 実行履歴・使用統計・解析（analytics）。
- N3. シェル補完スクリプトの生成（将来 M6+ 候補）。
- N4. 設定ファイルを書き換える `shiori add/edit/rm` 系サブコマンド。当面「登録＝設定ファイルを手で編集」とする（[§11 Q3](#11-レビュアーに判断を仰ぎたい点) で要判断）。
- N5. Windows ネイティブ対応。初期は Unix 系（Linux / macOS）に絞る（[§11 Q2](#11-レビュアーに判断を仰ぎたい点) で要判断）。
- N6. 複数設定ファイルのマージ（グローバル設定 + プロジェクト設定の合成など）。初期は「最も近い 1 ファイル」のみ。

## 4. 用語

- **登録済みコマンド / entry**: 設定ファイルに書かれた 1 件のコマンド定義。`name` で一意に識別する。
- **テンプレート**: `{{param}}` を含む引数を持つ entry。実行時に値を埋めて確定する。
- **argv**: `os/exec` にそのまま渡す引数文字列の配列（`["prisma","migrate",...]`）。

## 5. アーキテクチャ全体像

依存の向きは常に **UI → コア** の一方向。コアは UI・端末・フラグパーサを一切 import しません。

```
cmd/shiori/              エントリーポイント（薄い）。フラグ解釈と配線のみ。
  main.go

internal/
  config/                設定ファイルの探索・読み込み・パース・検証
  command/               ドメインモデル（Command, Param）。他の internal に依存しない純粋な型
  template/              テンプレート展開とパラメータ検証（インジェクション安全性の中心）
  runner/                実行。os/exec・シグナル・終了コード・context を扱う
  cli/                   CLI の各サブコマンド（list / run ...）。coreを呼ぶだけ
  (M5) tui/              Bubble Tea。cli と同じ core を呼ぶ
```

設計上の不変条件（レビューで守りたい点）:

- **UI の都合でコアに型やフィールドを足さない。** 例えば TUI の表示用フラグをコアの `Command` に入れない。表示整形は UI 層の責務。
- `command` パッケージは最下層。`config` はファイル I/O とパースのみを担い、ビジネスルール（実行可否など）は持たない。
- `runner` は「確定した argv」を受け取る。テンプレート展開（`template`）と実行（`runner`）を分離し、片方だけをテストできるようにする。

## 6. 設定スキーマ（データモデル）

採用形式は §7.1 の議論の結果として **YAML を第一候補**とします（要レビュー判断）。
以下は推奨形式での例です。TOML でも同じ構造を表現できます（§7.1 に対応表）。

```yaml
# shiori.yaml — プロジェクトルートに置く
version: 1

commands:
  - name: migrate
    description: Prisma のマイグレーションを作成する
    # argv。第0要素が実行ファイル。シェルは経由しない
    argv: [prisma, migrate, dev, --name, "{{name}}"]
    params:
      - name: name
        description: マイグレーション名
        required: true

  - name: deploy
    description: 本番へ反映する（確認あり）
    argv: [terraform, apply]
    confirm: true          # 実行前に確認を挟む

  - name: logs
    description: 直近ログを grep する（パイプが要るので shell 経由）
    shell: "docker compose logs --tail=200 | grep -i error"
    # shell を使う場合は argv ではなく 1 本の文字列。§7.3 / §7.4 参照
```

対応する Go の型（概略。フィールドは最小限に保つ）:

```go
// internal/command
type Command struct {
    Name        string
    Description string
    Argv        []string // shell を使わない場合のみ
    Shell       string   // shell: true 相当。空なら argv モード
    Params      []Param
    Confirm     bool
}

type Param struct {
    Name        string
    Description string
    Required    bool
    // 初期は値はすべて string 扱い（§11 Q4）
}
```

`argv` と `shell` は**排他**（両方指定・両方空はバリデーションエラー）。
YAML 上は `shell: true` のような bool ではなく「シェルスクリプト文字列」を直接持たせる案を採ります
（理由は §7.4：値をスクリプト本文に文字列結合させないため）。この是非も §11 Q1 で確認します。

## 7. 主要な設計判断

各項目は「選択肢 → 採用 → 理由 → 捨てた案と理由」で記述します。
準拠基準は Google Go Style Guide / Go Code Review Comments。該当する箇所は明記します。

### 7.1 設定ファイルの形式: YAML / TOML / JSON

**選択肢**

| 観点 | JSON (stdlib) | YAML (`gopkg.in/yaml.v3`) | TOML (`BurntSushi/toml`) |
| --- | --- | --- | --- |
| コメント | ✗ 不可 | ✓ | ✓ |
| 標準ライブラリのみ | ✓ `encoding/json` | ✗ 依存追加 | ✗ 依存追加 |
| ネストした commands/params の手書きやすさ | △ 冗長 | ◎ 自然 | △ array-of-tables が冗長 |
| スカラ推論の落とし穴 | なし | あり（Norway 問題等） | 少ない |
| 開発者の馴染み | 中 | 高（compose / Actions / k8s） | 中（cargo / pyproject） |

**採用（提案）: YAML。** ただし strict decode（`yaml.v3` の `KnownFields(true)`）で未知キーを拒否する。

**理由**

- shiori の設定の主役は「コマンドのリスト（各要素がネストした map と配列）」。この形は YAML が最も素直に読み書きできる。
- 想定ユーザーは YAML の開発ツール設定に既に慣れた開発者。学習コストが低い。
- YAML の落とし穴（`no` が false になる等）は、**スキーマを型付きの構造体に strict decode する**ことで実害をほぼ消せる。`argv` は文字列配列、`required` は bool と型が決まっており、未知キー・型不一致はパース時に弾ける。

**捨てた案**

- **JSON**: コメント不可が致命的。人が手で編集する設定ファイルで、各コマンドの意図をコメントで残せないのは体験として弱い。標準ライブラリで済む利点より欠点が大きい。
- **TOML**: 設定専用で落とし穴が少ない長所は魅力的。しかし `[[commands]]` の中にさらに `[[commands.params]]` を書く array-of-tables が、ネストが深いと読みにくい。「設定の主役がリスト」という本件の形には YAML が勝ると判断。

**依存追加の是非**: 良い形式には結局 stdlib 外の依存が要る（JSON を捨てる前提なら不可避）。
`gopkg.in/yaml.v3` は枯れており広く使われる。「標準ライブラリで足りるものは標準」という原則には、
「コメント付き人間向け設定という要件を JSON では満たせない」という理由で例外を置きます。
→ **これは §11 Q1 でレビュアーの判断を仰ぎます。**

### 7.2 設定ファイルの探索

**採用**: カレントディレクトリから親方向へ 1 階層ずつ遡り、最初に見つかった設定ファイルを採用（`.git` / `.editorconfig` と同じ発見方式）。

- ファイル名: `shiori.yaml`（`.yml` も許容）。先頭ドットなしを基本とする（可視で、プロジェクト設定であることを示すため）。
- 停止条件: ファイルシステムのルートに達したら打ち切り。見つからなければ「設定が無い」旨の明確なエラー。
- 複数候補が別階層に存在する場合: **最も近い（cwd に近い）1 ファイルのみ**採用。マージはしない（N6）。
- ループ・シンボリックリンク対策: `filepath.Dir` で辿り、親が自分自身になった（= ルート）時点で停止。無限ループを構造的に防ぐ。

**捨てた案**

- **固定パス（`~/.config/shiori/...`）のみ**: 「プロジェクトごとに違うコマンド」という中心的ユースケースに合わない。
- **環境変数でパス指定を必須**: 体験が悪い。ただし将来 `SHIORI_CONFIG` による明示上書きは拡張余地として残す（初期は非対応）。

### 7.3 コマンド実行モデル: 引数配列 vs シェル

**採用**: デフォルトは `os/exec` に **argv 配列**を渡し、シェルを経由しない。
`shell` を明示した entry のみ、シェル経由で実行する。

- argv モード: `exec.CommandContext(ctx, argv[0], argv[1:]...)`。シェルのメタ文字解釈・グロブ・単語分割が一切起きない。
- shell モード: `exec.CommandContext(ctx, "sh", "-c", script, ...)`。パイプ・リダイレクト・`&&` 等が必要なコマンド専用の、明示的なオプトイン。

**理由**

- argv 配列実行は、シェルインジェクションを**構造的に**不可能にする（パラメータ値がどんな文字列でも、常に argv の 1 要素にしかならない）。これが G5 の安全性の土台。
- シェルが本当に必要な場面（パイプ等）は確かにあるので、ゼロにはせず「明示的に宣言した時だけ」に限定して危険の総量を絞る。
- Go Code Review Comments の「明示性」「驚き最小」に沿う。`run` の挙動が entry を見れば分かる。

**捨てた案**

- **常にシェル経由（`sh -c "<文字列>"`）**: 実装は楽だが、全コマンドがインジェクション面になる。却下。
- **`shell: true`（bool）+ コマンド文字列は別フィールド**: 値をスクリプト文字列に結合する設計を誘発しやすい。§7.4 の理由から、shell モードは「スクリプト本文」を直接持つ形にする。

### 7.4 パラメータ付きテンプレートとインジェクション安全性

**テンプレート構文**: `{{name}}`（argv の各要素内に埋め込める）。

**argv モードの安全性（容易）**

- 展開は「argv 要素の文字列内で `{{name}}` を値に置換」するだけ。置換後も要素は 1 つのまま → シェル解釈が無いので、値に `;` や `$()` や空白が含まれても**別の引数やコマンドに化けない**。
- 例: `--name` の次要素 `"{{name}}"` に `"a; rm -rf /"` を入れても、プロセスには単一引数 `a; rm -rf /` が渡るだけ。

**shell モードの安全性（要注意）**

シェルスクリプト本文に値を**文字列結合しない**。代わりに `sh -c` の位置パラメータとして渡す:

```
sh -c '<script 本文（{{name}} を $1 に変換したもの）>' shiori "<name の値>"
```

- スクリプト本文中の `{{name}}` を `"$1"`（クォート済み位置パラメータ）に変換し、値そのものは `exec` の引数配列経由で渡す。値はシェルの字句解析を受けないため、メタ文字を含んでいても注入にならない。
- これにより「shell: true でもパラメータ値のインジェクションが起きない」を満たす。

**パラメータ検証（`template` パッケージの責務）**

- `required: true` の param が実行時に与えられなければエラー。
- テンプレートに現れる param が `params` に宣言されていない → 設定検証エラー（タイポ検出）。
- 宣言されたが未使用の param → 警告（エラーにはしない。要判断 §11）。
- param 名の文字種を制限（`[a-zA-Z_][a-zA-Z0-9_]*`）し、テンプレート構文解析を単純かつ曖昧性なく保つ。

**捨てた案**

- **`text/template` をそのまま流用**: 高機能すぎ（任意関数・条件分岐）で、設定ファイルがチューリング完全に近づく。shiori の「値を 1 つ埋める」用途には過剰。自前の最小構文で、仕様を読みやすく・攻撃面を小さく保つ。
- **shell モードで値を本文へ `fmt.Sprintf` 結合**: 典型的なインジェクション経路。明確に却下し、位置パラメータ方式を採る。

### 7.5 context・割り込み（Ctrl+C）・終了コードの伝播

**終了コード（G3）**

- 子が正常終了: `cmd.Run()` が `nil` → shiori も 0。
- 子が非ゼロ終了: `*exec.ExitError` から `ExitCode()` を取り出し、**その値で shiori を終了**する。
- 実行前エラー（実行ファイルが無い等）: shiori 自身のエラーとして、子の終了コードとは区別できる固定コード（例 125、`git`/`docker` の慣例に倣う）で終了。

**割り込み（G4）**

- `signal.NotifyContext(ctx, os.Interrupt)` でルート context を作り、`exec.CommandContext` に渡す。
- ただし `CommandContext` は既定で context キャンセル時に子へ **SIGKILL** を送る（graceful でない）。そこで:
  - 子プロセスを**独立したプロセスグループ**で起動（`SysProcAttr{Setpgid: true}`）し、
  - shiori が SIGINT を受けたら、まず子のプロセスグループへ **SIGINT を転送**して猶予を与え、一定時間後も残っていれば SIGKILL、という段階的終了にする。
- これにより、`vim` のような対話的・シグナルを自前処理する子にも中断が正しく伝わる。
- M5（TUI）では、対話的コマンド実行時に**端末の制御（前面プロセスグループ・raw/cooked）を子へ渡す**必要がある。設計上はここで分岐点になることだけ明記し、詳細は M5 の設計で詰める。

**理由 / 捨てた案**

- 「`CommandContext` に任せて SIGKILL」だけでは、未保存バッファを持つ対話的コマンドを強制終了してしまう。段階的シグナルにする。
- プロセスグループを分けるのは、shiori 自身が受けた SIGINT と、子ツリー全体への転送を制御可能にするため。分けないと端末から子へ直接 SIGINT が二重に届く等、挙動が読みにくくなる。

### 7.6 破壊的コマンドの確認

**採用**: entry に `confirm: true` を持たせ、実行直前に「本当に実行するか」を確認する。

- 確認は UI 層の責務（CLI はプロンプト、TUI はモーダル）。コアは「このコマンドは確認が要る」という事実（`Command.Confirm`）だけを持ち、**どう尋ねるかは知らない**。これで G9（UI 非依存）を保つ。
- 非対話環境（標準入力が TTY でない、CI など）では **fail-closed**（実行せずエラー）を既定にする。`--yes` 相当のオプトインがあれば実行可。
- 確認プロンプトに、埋め込んだパラメータ値を出すか？ → 秘匿値の可能性があるため、**既定では展開後の完全な argv を出さない**（§7.7）。コマンド名と説明を示す。

### 7.7 秘匿値の扱い（ログ・エラー）

**原則**: パラメータ値・環境変数の値を、ログ・エラーメッセージ・確認プロンプトに不用意に出さない（G8）。

- 実行失敗時のエラーは「どの entry が、終了コードいくつで失敗したか」を伝える。**展開後の argv 全体はデフォルトでは出さない**（値にトークンやパスワードが入りうる）。
- デバッグが必要な場合に限り、ユーザーが明示的に `--verbose`（または `SHIORI_DEBUG`）を立てたときだけ、展開後 argv を出す。既定は安全側。
- param に `secret: true` を付けられるようにするかは将来拡張（初期は「値は常に出さない」で一律安全側）。

**トレードオフ**: 既定で値を隠すとデバッグしづらい。これは「安全 > 利便」を既定にし、オプトインで利便を取り戻す設計で解決する。Go Code Review Comments の「エラーは有用に、しかし機密を漏らさない」方針に沿う。

## 8. マイルストーン別の計画

各マイルストーンは PR 単位でレビューを通す。1 PR ≤ 200 行を原則とし、超える場合は分割提案する。

- **M0（本書）**: Design Doc。コードなし。
- **M1**: `config`（探索・読み込み・strict decode・検証）+ `command` モデル + `shiori list`。
- **M2**: `runner`（argv 実行・終了コード伝播・context/中断）+ `shiori run <name>`。
- **M3**: `template`（テンプレート展開・param 検証・入力）。argv モードのみ。
- **M4**: `shell` モードのオプトインと位置パラメータ方式、`confirm` 確認。
- **M5**: Bubble Tea TUI（検索・選択・実行・出力表示、端末制御の委譲）。

M1〜M4 は依存の少ない下層（config/command → template → runner）から積む。

## 9. テストと CI

- テストは**テーブル駆動**で書く（Go の慣行）。特に `template`（展開・インジェクション非発生）、`config`（探索・strict decode・検証エラー）、`runner`（終了コード・中断）を重点的に。
- `runner` の実行系テストは、`go` ビルド可能なヘルパープロセス方式（`TestMain` + 環境変数で分岐する定番パターン）で、実在コマンドに依存せず決定的に書く。
- CI 必須ゲート: `gofmt`（差分ゼロ）、`go vet`、`staticcheck`、`go test -race`。
- 依存は最小限。追加する場合は PR に理由と代替案を明記する（本書 §7.1 の YAML 依存が最初の対象）。

## 10. 代替アーキテクチャ（検討して捨てた全体方針）

- **プラグイン / スクリプトで拡張可能な実行エンジン**: 柔軟だが複雑で攻撃面が広い。shiori は「登録済みコマンドを安全に実行する」小さな道具に徹する。却下。
- **コアを持たず各 UI に直接ロジックを書く**: 3 つの入り口で実装が重複し、挙動がずれる。コア単一化（G9）を選ぶ。

## 11. レビュアーに判断を仰ぎたい点

実装着手前に、以下について判断をお願いします。選択肢とトレードオフを添えます。

- **Q1. 設定ファイルの形式**: 提案は **YAML + strict decode**（§7.1）。
  「`gopkg.in/yaml.v3` という stdlib 外依存を最初から入れる」ことの是非を含めて判断ください。
  TOML（落とし穴は少ないがネスト表現が冗長）を推される場合、理由があれば差し替えます。
- **Q2. 対応 OS の初期スコープ**: 初期を **Unix 系のみ**（N5）とし、プロセスグループ・シグナル設計を Unix 前提で単純化したいです。
  Windows を初期から含めると §7.5 の設計が分岐し複雑化します。初期 Unix 限定で良いか。
- **Q3. コマンド「管理」の範囲**: 当面「登録＝設定ファイルを手編集」（N4）とし、`shiori add/rm` は後回しにしたいです。
  「管理」を要件に含める以上、早期に CLI 編集を入れるべきか、手編集で十分か。
- **Q4. パラメータの型**: 初期は**すべて string**（§6）。数値・enum・デフォルト値・`secret` などは将来拡張としたいです。初期スコープの線引きの確認。
- **Q5. shell モードの表現**: `shell: true`（bool）+ 別フィールドではなく、**`shell:` にスクリプト文字列を直接持たせる**案（§6 / §7.4）を採りたいです。値を本文へ結合させない設計のためですが、設定の見た目として許容できるか。
